The builder is on with a Git catalog in pull request or commit mode (see [Templates]({{< relref "/docs/features/templates#where-templates-live" >}})), or with `TEMPLATE_EDITOR=1` for `TEMPLATES_DIR`. Only admins can use it, because a template decides which module the runners execute.

1. Open **+ New template** (`/templates/new`) or **edit** on any template.
2. Choose **Start from a registry module** and the module source, version and one form field per variable are filled in for you. A `list(object({...}))` of strings, numbers and bools becomes a **List of rows** field and an `object({...})` a **Group of fields**: their fields come from the variable's type (give each a label in the card); `list(string)` and `set(string)` become **List of text**, `map(string)` **Key / value**; other complex types (lists of lists, maps of objects) are flagged, not generated. A string variable's `validation` written as `can(regex("<literal>", var.<name>))` fills its pattern; other conditions stay with Terraform, which checks them at plan time. Patterns use Go (RE2) syntax, but the browser checks them as JavaScript regular expressions: Go-only syntax such as `(?i)` makes the browser skip its check, and the server still rejects values that don't match.
3. Or type a `git::` source and ref by hand, then add one card per form field: variable name, label, help, type (Text, Number, Yes / no, Dropdown), and the settings that type uses: dropdown options (one row each: the value Terraform gets, and optionally the name end users see, e.g. `Standard_D2s_v5` shown as *Small (2 vCPU, 8 GB)*), default (a number field for Number, yes / no / none for Yes / no, suggesting a dropdown's options), pattern, required (not for dropdowns and Yes / no, which always have a value), sensitive, **Per environment** (each project may set the value, see [Environments and promotion]({{< relref "/docs/features/environments#per-environment-inputs" >}}); not with sensitive or the module name field), and **Module name from** (the field whose value names the template's `module.<name>` in a workspace). Hover a setting's name, or focus its field, for help. Write the rule a pattern checks in **Help** (e.g. label `Account name`, help `3-24 lowercase letters or digits.`): end users see it under the field, and as the error when a value doesn't fit. Fields generated from a registry module get their label and help from the variable's description, split at its first `: `. Reorder fields with ↑ ↓ and remove them with ✕ (or clear the variable name).
4. To ask only what matters, set a field's **Show** row to *when &lt;field&gt; is* and pick the values (click the chips, or type them comma-separated). Only dropdowns and Yes / no fields (values `true`, `false`) above the field can be picked. See [conditional inputs]({{< relref "/docs/features/templates#conditional-inputs" >}}).
5. **Preview form** opens the deploy form end users get, from the unsaved builder, in a new tab. It saves nothing and can't be submitted.

Each new template gets a random UUID as its id, kept when the page is saved again (e.g. after its pull request opened). Saving writes the [1.0 format]({{< relref "/docs/features/templates#template-format" >}}) (typed defaults, `help`, `"$schema"`), runs the same validation as loading, checks that a referenced registry version exists, and then opens a pull request or commits `<folder>/<id>.json` (Git catalog), or writes it into `TEMPLATES_DIR` and shows the generated deploy form right away. An edited template keeps its file name.
